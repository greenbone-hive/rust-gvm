# Migrating from v0.6.0 to v0.7.0

`v0.7.0` is the next downstream-ready release line and is intentionally
SemVer-incompatible with `v0.6.0`. The project remains a pre-1.0 Technology
Preview, so the minor-version change is the breaking-version signal. The
release is not published yet: issue
[#602](https://github.com/greenbone-hive/rust-gvm/issues/602) must finish its
canonical-request audit and `rust-gvm-api#457` must validate the final surface
first.

This guide records migrations from the last published release. It will expand
as the remaining #602 families move to canonical complete request values. The
full typed-execution background and examples remain in
[typed-execution-migration.md](typed-execution-migration.md).

## Filters

The six filter lifecycle operations now accept complete request values. The
parallel `FilterOpts`, `GetFiltersOpts`, free XML builders, and split-argument
client signatures from `v0.6.0` are removed.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetFiltersOpts` | `GetFiltersRequest` |
| filter ID passed directly to `get_filter` | `GetFilterRequest` |
| name plus `FilterOpts` passed to `create_filter` | `CreateFilterRequest` |
| filter ID plus `FilterOpts` passed to `modify_filter` | `ModifyFilterRequest` |
| filter ID plus clone options | `CloneFilterRequest` |
| filter ID plus `ultimate` flag | `DeleteFilterRequest` |

For example:

```rust
use gvm_gmp::commands::filters::CreateFilterRequest;
use gvm_gmp::FilterType;

let mut request = CreateFilterRequest::new("Recent tasks");
request.term = Some("rows=10 sort-reverse=modified".into());
request.filter_type = Some(FilterType::Task);
let created = client.create_filter(request).await?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

### Replacing `sort_order`

Do not carry the old `FilterOpts::sort_order` field forward. Current gvmd does
not accept a `<sort_order>` child in `create_filter` or `modify_filter`.
Sorting is part of the filter term instead:

- use `sort=<field>` for ascending order;
- use `sort-reverse=<field>` for descending order.

The canonical requests deliberately cannot encode the unsupported child. This
is a protocol-drift correction, not removal of a gvmd sorting capability. See
the [pinned gvmd evidence](filter-request-gvmd-evidence.md) for the schema and
parser references.

Low-level callers that need unmodeled GMP XML can continue to use `send` or
`call`, but gvmd remains authoritative and may reject unsupported elements.

## Alerts

All eight alert operations now accept complete request values. `AlertOpts`,
`GetAlertsOpts`, `TriggerAlertOpts`, the eight free XML builders, and the
split-argument client signatures from `v0.6.0` are removed.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetAlertsOpts` | `GetAlertsRequest` |
| alert ID passed directly to `get_alert` | `GetAlertRequest` |
| name plus `AlertOpts` passed to `create_alert` | `CreateAlertRequest` |
| alert ID passed directly to `clone_alert` | `CloneAlertRequest` |
| alert ID plus `AlertOpts` passed to `modify_alert` | `ModifyAlertRequest` |
| alert ID plus `ultimate` flag | `DeleteAlertRequest` |
| alert ID passed directly to `test_alert` | `TestAlertRequest` |
| alert/report IDs plus `TriggerAlertOpts` | `TriggerAlertRequest` |

Create now requires the event, condition, and method in its constructor because
gvmd rejects a final request without them:

```rust
use gvm_gmp::commands::alerts::{AlertData, CreateAlertRequest};
use gvm_gmp::{AlertCondition, AlertEvent, AlertMethod};

let mut request = CreateAlertRequest::new(
    "Finished scan",
    AlertEvent::TaskRunStatusChanged,
    AlertCondition::Always,
    AlertMethod::Email,
);
request.event_data.push(AlertData::new("status", "Done"));
request
    .method_data
    .push(AlertData::new("to_address", "ops@example.com"));
let created = client.create_alert(request).await?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

`ModifyAlertRequest::filter_id` follows gvmd's unusual replacement behavior:
omitting it clears the current alert filter. Pass the existing filter ID when
the binding must be preserved. Omitted `active` still preserves the current
active state. See the [pinned gvmd evidence](alert-request-gvmd-evidence.md).

## Schedules

The six schedule lifecycle operations now accept complete request values.
`ScheduleOpts`, `GetSchedulesOpts`, eight free XML builders, the duplicate
`CreateTypedScheduleRequest` / `ModifyTypedScheduleRequest` wrappers, and the
raw-versus-typed facade split from `v0.6.0` are removed.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetSchedulesOpts` | `GetSchedulesRequest` |
| schedule ID passed directly to `get_schedule` | `GetScheduleRequest` |
| name plus `ScheduleOpts` passed to `create_schedule` | `CreateScheduleRequest` |
| name plus `ScheduleInput` passed to `create_typed_schedule` | `CreateScheduleRequest::from_input` |
| schedule ID passed directly to `clone_schedule` | `CloneScheduleRequest` |
| schedule ID plus `ScheduleOpts` passed to `modify_schedule` | `ModifyScheduleRequest` |
| schedule ID plus `ScheduleInput` passed to `modify_typed_schedule` | `ModifyScheduleRequest::from_input` |
| schedule ID plus `ultimate` flag | `DeleteScheduleRequest` |

Raw iCalendar remains supported through the canonical constructors:

```rust
use gvm_gmp::commands::schedules::CreateScheduleRequest;

let mut request = CreateScheduleRequest::new(
    "Monthly scan",
    "BEGIN:VCALENDAR\r\nVERSION:2.0\r\nEND:VCALENDAR",
);
request.timezone = Some("Europe/Berlin".into());
let created = client.create_schedule(request).await?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

Create and modify both require a non-empty final iCalendar payload. This
matches the gvmd handler; notably, the handler requires modify iCalendar even
though the schema marks that child optional. See the
[pinned gvmd evidence](schedule-request-gvmd-evidence.md).

## Scanners

The seven scanner operations now accept complete request values.
`ScannerOpts`, `GetScannersOpts`, the seven free XML builders, and the
split-argument client signatures from `v0.6.0` are removed.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetScannersOpts` | `GetScannersRequest` |
| scanner ID passed directly to `get_scanner` | `GetScannerRequest` |
| name plus `ScannerOpts` passed to `create_scanner` | `CreateScannerRequest` |
| scanner ID passed directly to `clone_scanner` | `CloneScannerRequest` |
| scanner ID plus `ScannerOpts` passed to `modify_scanner` | `ModifyScannerRequest` |
| scanner ID plus `ultimate` flag | `DeleteScannerRequest` |
| scanner ID passed directly to `verify_scanner` | `VerifyScannerRequest` |

Create now requires the fields gvmd requires for ordinary creation:

```rust
use gvm_gmp::commands::scanners::CreateScannerRequest;
use gvm_gmp::ScannerType;

let request = CreateScannerRequest::new(
    "Remote scanner",
    "scanner.example",
    9390,
    ScannerType::OpenVasScanner,
);
let created = client.create_scanner(request).await?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

Relay host/port fields are now available on create, modify, and scanner
responses. `ModifyScannerRequest::credential_id` uses `ScalarUpdate` so
omission preserves the relationship and `Clear` detaches it. Explicit empty
comment, CA, and relay-host values clear those fields. See the
[pinned gvmd evidence](scanner-request-gvmd-evidence.md).

## Notes and overrides

The six note and six override lifecycle operations now accept complete request
values. `NoteOpts`, `ModifyNoteOpts`, `GetNotesOpts`, `OverrideOpts`,
`ModifyOverrideOpts`, `GetOverridesOpts`, all twelve free XML builders, and the
split-argument client signatures from `v0.6.0` are removed.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetNotesOpts` / `GetOverridesOpts` | `GetNotesRequest` / `GetOverridesRequest` |
| resource ID passed directly to detail helpers | `GetNoteRequest` / `GetOverrideRequest` |
| NVT/text plus create options | `CreateNoteRequest` / `CreateOverrideRequest` |
| resource ID passed directly to clone helpers | `CloneNoteRequest` / `CloneOverrideRequest` |
| resource ID plus modify options | `ModifyNoteRequest` / `ModifyOverrideRequest` |
| resource ID plus `ultimate` flag | `DeleteNoteRequest` / `DeleteOverrideRequest` |

Create note requires NVT and text. Create and modify override also require the
numeric replacement severity that gvmd needs:

```rust
use gvm_gmp::commands::notes::CreateNoteRequest;
use gvm_gmp::commands::overrides::CreateOverrideRequest;

let note = client
    .create_note(CreateNoteRequest::new("1.3.6.1.4.1.25623.1.0.12345", "triage"))
    .await?;
let override_ = client
    .create_override(CreateOverrideRequest::new(
        "1.3.6.1.4.1.25623.1.0.12345",
        "accepted risk",
        0.0,
    ))
    .await?;
# let _ = (note, override_);
# Ok::<(), Box<dyn std::error::Error>>(())
```

On modify, omitted hosts, port, original severity, task, and result clear those
restrictions; omitted NVT and activation preserve them. The unsupported legacy
note `orphan` child is removed. See the
[pinned gvmd evidence](note-override-request-gvmd-evidence.md).

## Users and groups

All twelve user/group lifecycle operations now accept complete request values.
`UserOpts`, `ModifyUserOpts`, `GetUsersOpts`, `GroupOpts`, `GetGroupsOpts`, the
free XML builders, and split-argument client signatures are removed. The named
client helpers accept the same requests as `execute`.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetUsersOpts` / `GetGroupsOpts` | `GetUsersRequest` / `GetGroupsRequest` |
| user/group ID passed to free detail builders | `GetUserRequest` / `GetGroupRequest` |
| name plus `UserOpts` / `GroupOpts` | `CreateUserRequest` / `CreateGroupRequest` |
| user/group ID passed to free clone builders | `CloneUserRequest` / `CloneGroupRequest` |
| user ID plus `ModifyUserOpts` (or converted `UserOpts`) | `ModifyUserRequest::new(user_id, host_access)` plus optional updates |
| group ID plus `GroupOpts` passed to the free modify builder | `ModifyGroupRequest::new(group_id, name, comment, users)` with final values |
| user ID plus `ultimate` passed to the free delete builder | `DeleteUserRequest::new(user_id)`; remove the boolean |
| group ID plus `ultimate` passed to the free delete builder | `DeleteGroupRequest::new(group_id, ultimate)` |

Move optional create/update fields onto the requests. The old user `auth_type`
becomes `auth_source`, encoded as `<sources><source>…</source></sources>` in
place of the unsupported `<authentication>` child. User creation now also
supports `group_ids`; modification uses `CollectionUpdate::Omitted`,
`Replace`, or `Clear` for both roles and groups.

User modification requires the final `UserHostAccess`: gvmd replaces host
access on every modification, so pass the existing value when preserving it.
Group modification requires the final name, comment, and membership; empty
comment and users explicitly clear them. See the
[canonical migration example](typed-execution-migration.md#user-and-group-families).
Password diagnostics and wire traces remain redacted.

### Delete-user selectors, inheritance, and removal of `ultimate`

The v0.6.0 surface exposed deletion through the free
`delete_user(&user_id, ultimate)` builder; it had no typed
`GmpClient::delete_user` helper. Builder/send call sites migrate to
`DeleteUserRequest::new(user_id)` for **both** `ultimate = false` and
`ultimate = true`, using `execute` or the current named client helper. There is
no replacement boolean or trash-mode field.
The old builder serialized the attribute, but pinned gvmd does not parse it,
its schema omits it, and its management function has no ultimate argument.
The stale internal C struct member does not establish support. This intentional
removal is documented in the
[pinned schema/source evidence](user-group-request-gvmd-evidence.md#user-deletion-has-no-ultimate-input).

The canonical request also exposes the supported name and inheritance inputs
that were absent from the old two-argument builder:

| Selection | Canonical input | Wire attribute |
| --- | --- | --- |
| User by ID | `DeleteUserRequest::new(user_id)` | `user_id` |
| User by name | `DeleteUserRequest::by_name(name)` | `name` |
| Inheritor by ID (including `self`) | `request.inheritor_id = Some(id)` | `inheritor_id` |
| Inheritor by name | `request.inheritor_name = Some(name)` | `inheritor_name` |
| No explicit inheritance | Leave both inheritor fields `None` | Neither inheritor attribute |

Set exactly one user selector and at most one inheritor selector. The typed
request rejects ambiguous combinations before transport, even though gvmd gives
IDs precedence. For example, selecting by name and transferring owned resources
to a named inheritor encodes only supported attributes:

```rust
use gvm_gmp::commands::users::DeleteUserRequest;
use gvm_gmp::{GmpRequestCodec, GmpVersion};

let mut request = DeleteUserRequest::by_name("alice");
request.inheritor_name = Some("admin".into());
assert_eq!(
    request.encode(GmpVersion(22, 8))?,
    br#"<delete_user inheritor_name="admin" name="alice"/>"#,
);
# Ok::<(), Box<dyn std::error::Error>>(())
```

## Roles and permissions

All twelve operations now take their corresponding complete `*Request` value.
The four old option bags (`RoleOpts`, `GetRolesOpts`, `PermissionOpts`, and
`GetPermissionsOpts`) and twelve free XML builders are removed.

| Previous input | Canonical input |
| --- | --- |
| list options | `GetRolesRequest` / `GetPermissionsRequest` |
| detail ID | `GetRoleRequest` / `GetPermissionRequest` |
| role name plus options | `CreateRoleRequest::new(name)` plus request fields |
| permission options | `CreatePermissionRequest::new(name, PermissionSubject)` plus request fields |
| clone ID | `CloneRoleRequest` / `ClonePermissionRequest` |
| role ID plus optional modifications | `ModifyRoleRequest::new(id, final_name, final_comment, final_users)` |
| permission ID plus options | `ModifyPermissionRequest::new(id)` plus optional fields |
| ID and ultimate flag | `DeleteRoleRequest` / `DeletePermissionRequest` |

Role modification is replacement: supply the final name, comment, and users.
Permission modification preserves omitted fields. Empty comment clears;
`resource_id = ScalarUpdate::Clear` removes the resource. Subject and resource
identifier/type updates remain independently expressible. `Super` creation
requires an identity resource type; ordinary permission resources can omit type.
Role clones omit user membership. Only role clones support renaming; omission
selects gvmd's first available `<existing name> Clone <number>` name, while an
explicit active-name collision returns 400 without copying the role or its
permissions. A name held only in the trash is reusable. Empty clone comments
preserve the original for both families. Clearing a stored `Super` permission's
resource fails with the gvmd resource-not-found response and atomically
preserves the stored values. If the clear also supplies a non-identity type,
gvmd validates that type first and returns 400 with the same rollback guarantee.

See the [complete migration example](typed-execution-migration.md#role-and-permission-families)
and [pinned gvmd evidence](role-permission-request-gvmd-evidence.md). This bounded
slice preserves raw/custom execution, response associations, support outcomes,
and the frozen ticket surface; the v0.7 pre-release gates above remain in force.

## Assets, hosts, and operating-system assets

The thirteen supported asset-family operations now accept complete request
values. `CreateAssetOpts`, `DeleteAssetOpts`, `GetAssetsOpts`,
`ModifyAssetOpts`, `HostOpts`, `GetHostsOpts`, and
`GetOperatingSystemsOpts` are removed, along with all thirteen public free
builders in these modules.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| optional generic type through `GetAssetsOpts` | required `GetAssetsRequest::new(asset_type)` |
| host/OS list options | fields on `GetHostsRequest` / `GetOperatingSystemAssetsRequest` |
| create type plus optional `value` | `CreateAssetRequest::new(ip)` / `CreateHostRequest::new(ip)` |
| ID plus modify options/value | `ModifyAssetRequest::new(id, final_comment)` / `ModifyHostRequest::new(id, final_comment)` |
| ID plus delete options/`ultimate` | ID-only delete request |
| OS ID plus comment | no supported replacement; remove OS modification |

Generic reads require a type. List requests retain filter text, saved-filter ID,
details, and add `ignore_pagination`; the duplicate `type_` alias and typed
asset `trash` field are removed. Direct creation always creates a host from one
IPv4 or IPv6 address, preserves accepted spelling, and rejects empty text, DNS
names, ranges, CIDRs, lists, and malformed addresses before transport.

Modification replaces the final host comment and always emits `<comment>`;
empty text clears. Deletion is permanent and has no `ultimate` mode. Both old
boolean values migrate to the same ID-only request. An OS asset cannot be
modified through `modify_asset`, and referenced OS assets cannot be deleted.

```rust
use gvm_gmp::commands::hosts::{
    CreateHostRequest, DeleteHostRequest, GetHostRequest, ModifyHostRequest,
};

let created = client
    .create_host(CreateHostRequest::new("192.0.2.10"))
    .await?;
let id = created.id;
client
    .modify_host(ModifyHostRequest::new(id.clone(), "inventory host"))
    .await?;
let host = client.get_host(GetHostRequest::new(id.clone())).await?;
client.delete_host(DeleteHostRequest::new(id)).await?;
# let _ = host;
# Ok::<(), Box<dyn std::error::Error>>(())
```

Raw `send`/`call` remains available after free-builder removal. Asset OS
(`get_assets type="os"`) remains distinct from SecInfo OS and report OS
projections. See [pinned gvmd evidence](asset-request-gvmd-evidence.md) and the
[full migration notes](typed-execution-migration.md#asset-host-and-operating-system-asset-families).

## Results

Result list/detail retrieval now uses two complete canonical requests.
`GetResultsOpts` and the two public free builders are removed.

| v0.6.0 input | v0.7.0 input |
| --- | --- |
| `GetResultsRequest::new(GetResultsOpts { ... })` | fields directly on `GetResultsRequest { ..., ..Default::default() }` |
| `client.get_results(opts)` | `client.get_results(request)` |
| `client.get_result(&id)` | `client.get_result(GetResultRequest::new(id))` |
| `get_results(opts)` / `get_result(&id)` free builders | `client.execute(request)` or deliberate raw/custom execution |

```rust
use gvm_gmp::commands::results::{GetResultRequest, GetResultsRequest};
use gvm_gmp::EntityId;

let mut request = GetResultsRequest::default();
request.filter_string = Some("task_id=task-1 rows=20".into());
request.overrides_details = Some(true);
let results = client.get_results(request).await?;

let result_id = EntityId::new("result-1")?;
let result = client
    .get_result(GetResultRequest::new(result_id))
    .await?;
# let _ = (results, result);
# Ok::<(), Box<dyn std::error::Error>>(())
```

Root `task_id` is rendering context, not list selection; task/report
selection remains filter text. Expansion-detail flags do not request inclusion
and do not apply overrides: `notes`, `overrides`, and
`apply_overrides` remain separate filter controls. Counts can be absent when
`get_counts=0`.

Trash, root report selection, lean/delta rendering, pagination bypass, and
root inclusion/application convenience fields have no canonical replacement.
The typed `ScanResult` remains a bounded projection and omits complete nested
note/override, ticket, detection, tag, delta, and original-severity payloads.
Raw `send`/`call`, `XmlCommand`, `gvm_protocol::Request`, and custom
`GmpRequestCodec` implementations remain supported for intentionally
unmodeled XML. See the
[full migration notes](typed-execution-migration.md#result-list-and-detail-family)
and [pinned evidence](result-request-gvmd-evidence.md).

## Report configurations

Report-configuration lifecycle calls now take six complete canonical requests.
The old option bags, nine free builders, three option-bearing wrappers, three
redundant facade variants, and five raw `Gmp226Commands` methods are removed.

| v0.6.0/transitional input | v0.7.0 input |
| --- | --- |
| `get_report_configs_parsed(opts)` | `get_report_configs(GetReportConfigsRequest { ... })` |
| `get_report_config(&id)` | `get_report_config(GetReportConfigRequest::new(id))` |
| `create_report_config(name, format)` / `_with_opts(...)` | `create_report_config(CreateReportConfigRequest::new(name, format_id))` |
| `clone_report_config(&id)` | `clone_report_config(CloneReportConfigRequest::new(id))` |
| `modify_report_config(&id, opts)` | `modify_report_config(ModifyReportConfigRequest::new(id))` |
| `delete_report_config(&id)` / `_with_opts(...)` | `delete_report_config(DeleteReportConfigRequest::new(id))` |
| raw `Gmp226Commands` lifecycle method returning `Response` | canonical typed facade or `execute(request)` returning the associated typed response |

Selectors now use `EntityId` without imposing UUID-only client validation.
Move root `first`/`rows` into filter text, including `rows=-1`. Direct creation
uses `<report_format id="..."/>`; the old `<report_format_id>` child is not
accepted by gvmd.

`ReportConfigParamValue::Value("")` assigns an empty value,
`UseDefault` resets one named override, and omission leaves it unchanged on
modify. Empty comments clear; omitted comments preserve. Clone accepts only an
optional name override, with omitted/empty names requesting automatic naming.
There is no report-config import, preference wrapper, usage type, policy field,
or modify-format replacement.

The typed response exposes configuration metadata and its format association,
including ID-only orphan references, but not parameter values/defaults/options,
`using_default`, orphan state, or full permission/tag expansion. Use raw
`send`/`call`, `XmlCommand`, `gvm_protocol::Request`, or a custom codec for
deliberately unmodeled XML. Source quirks and bounded mock approximations are
separate from compatibility claims; see the
[full migration notes](typed-execution-migration.md#report-configuration-lifecycle)
and [pinned evidence](report-config-request-gvmd-evidence.md).
